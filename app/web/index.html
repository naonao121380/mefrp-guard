mefrp 上未纳管的隧道

这些隧道存在于你的 mefrp 账号里，但还没有被本程序管理。可以点「纳管」把它绑到一条记录上。

节点

mefrp
两类隧道用的是两套独立的偏好（区域 / 带宽 / 负载 / 冷却 / 关键词都各一份）， 所以同一个节点在这里可能一边「自动择优可用」、另一边「可手动指定」。切上面的页签看对应的口径。

这一页是 mefrp 纳管的节点。 外部节点（自建 frps 或别的 frp 服务商）不在这里常驻 —— 它们是隧道的附属信息， 在「隧道」页点「从 frpc 配置导入」粘贴一份配置就能用，用完删掉隧道即可。

以后如果接了别家有开放 API 的 frp 服务商，这里会再加一个子页签 （一家一个）；现在只有 mefrp 一家，所以没有子页签。

frpc 实例

一个 frpc 进程只能连一个节点，所以 同一个实例承载的隧道必须落在同一个节点上。 自动切换时，该实例的全部隧道会一起搬到新节点，然后只重启它自己的容器 —— 其它实例完全不受影响。

引擎节奏

两类隧道都要小心，原因正好相反：
· UDP 在节点上监听的是 UDP 端口，没有 TCP 监听 —— 用 TCP 去探必然失败，会让健康隧道被反复判定为故障、触发无意义的切换。
· HTTP/HTTPS 反过来：节点反代对任何域名都会握手成功，TCP 探出来永远是「通」（假阳性），等于白探。要真探就得选「按类型」，它会去请求你的绑定域名，返回 2xx/3xx 算通。
保持「自动」最安全；想给 HTTP 隧道做真实探测再切「按类型」。
默认请求根路径 /。若你的服务在根路径上返回 4xx/5xx（比如必须带特定路径才返回 200），把它改成能返回 2xx 的路径，否则会被判成故障。
网络抖一下不该惊动你。连续失败满这个时长，才把「拉取 mefrp 状态失败 / DNS 同步失败」升成红色告警；在那之前只在事件里留一条黄色 warn。恢复则要连续正常满 10 分钟才算数（抖动源下「一轮正常」不算恢复，否则告警永远攒不满）。默认 1800（30 分钟）。填 0 = 一失败就告警。
DNS 记录只在节点地址变了的时候需要改，而地址很少变 —— 所以平时按这个间隔核对一次就够（默认 900 = 15 分钟），地址一变立刻同步、不等间隔。原来的「每轮都核对」（20 秒一次）会为每条隧道持续打 Cloudflare API，纯属白费；填 0 = 退回那个行为。

节点择优 · TCP / UDP

TCP/UDP 隧道靠端口工作，所以这套偏好只关心「节点能不能给一个可用的端口」。

节点择优 · HTTP / HTTPS

HTTP/HTTPS 隧道靠域名工作（节点反代按域名分流），所以是另一套独立的偏好。 ⚠️ 默认只用港澳台 + 海外节点：官方文档明说大陆节点建 HTTP/S 站需要向管理员报备域名（白名单）， 腾讯云/阿里云/华为云等节点还要求域名在服务商处接入备案。避开大陆能让新建的 HTTP 隧道直接可用， 而不是建完发现打不开。已经报备过、或域名已备案的话，可以把「中国大陆」勾上。

节点偏好

按节点名称里包含的字排序（包含匹配，不是相等）—— mefrp 节点名形如「北京BGP-1」，填「北京」两个字就够。 靠上的优先：填了「北京」和「上海」时，北京的所有节点排在上海之前。 一个都没命中的节点排在最后，但仍会被选中 —— 偏好是排序，不是筛选。 匹配范围：节点名称 + 描述 + 区域。两套偏好各有一份，下面可切换。

行为开关

账号安全

改用户名或密码需要先输入当前密码。改完后，其他设备上的登录会全部失效，需要重新登录 —— 这是有意的，否则旧密码泄露期间建立的会话在改密码后依然有效。

节点描述

新增隧道

HTTP/HTTPS 隧道没有远程端口 —— 对外入口就是这个域名。 你需要把这个域名解析到节点：在 Cloudflare 里加一条记录指向节点地址 （节点地址是 IP 就写 A 记录，是域名就写 CNAME）， 节点反代会按域名（Host 头）把请求转给这条隧道。本程序会在你填了「关联的 Cloudflare 记录名」时自动帮你维护它。
⚠️ 证书装在节点那一侧，不是你本地。免费用户基本用不上 —— 要 HTTPS 建议用 http 隧道 + Cloudflare 终结 TLS（橙云代理）。
模型是一条隧道 : 一个 frpc 容器。没挂接的隧道不会被写进任何 frpc 配置， 也就没人帮它改配置、重启容器 —— 必须显式指定，程序不会替你猜。
保存后，如果 mefrp 上还没有同名的隧道，程序会自动在你的账号上创建一条；如果已存在同名隧道，则会直接接管它。

手动切换隧道

留空 = 走自动择优（带宽 ≥ 阈值、负载达标、命中优先关键词的排前面）。 指定节点会绕过冷却期与排除名单，但仍需满足用户组权限与带宽/负载门槛。

切换过程：删旧隧道 → 新建隧道 → 重建该 frpc 实例的配置 → 重启它的容器 → 端到端验证 → 更新 DNS。整个流程要几十秒。

为什么是「先删后建」：mefrp 上同名隧道不能共存，不先删掉旧的就会直接撞名失败。 代价是这条隧道在中间那几步会短暂完全不可用 —— 它本来就已经是坏的了，所以可以接受； 但如果新建失败，程序会把旧的重新建回原节点，不会让它凭空消失。

新增 frpc 实例

必须是绝对路径（相对路径会随进程工作目录变化），而且不能和别的实例重复 —— 两个实例共用一个配置文件会互相覆盖。容器里跑的话填容器内看到的路径（也就是挂载点）。

从 frpc 配置导入隧道

标签只用来分组筛选，不参与任何自愈逻辑。mefrp 纳管的隧道 会自动打 mefrp；外部节点的隧道留空，你想叫什么就叫什么。

把这个 frpc 实例改连到外部节点

做的事：改写这个实例配置里的服务端段（地址 / 端口 / 鉴权） → 按上面的选择决定是否重启它的容器 → 重新解析相关隧道的 DNS。 隧道定义一个字都不动 —— 换的只是「哪台 frps 来接」。

为什么是实例级而不是隧道级：一个 frpc 进程只能连一个 serverAddr， 所以「哪台 frps 来接」这件事只在这个实例身上说得通。它承载的隧道会一起过去； 其它实例连的是各自配置里的地址，完全不受影响。
