# mefrp-guard

给 [mefrp](https://www.mefrp.com/) 隧道用的**自动故障转移守护程序**。

盯着你的隧道，节点挂了就自动换节点、改 frpc 配置、重启容器、同步 Cloudflare DNS，并把过程推到 Gotify。

> 📖 想看内部实现、mefrp API 的坑、设计取舍、测试与排错 → **[README.dev.md](README.dev.md)**（技术留档）

---

## 它解决什么问题

mefrp 的免费节点会不定期下线、维护、被禁用。手工处理一次故障要六步：

| 步骤 | 原来手工做 | 装了本程序 |
|:---:|---|---|
| 1 | 上 mefrp 网页看哪个节点挂了 | ✅ 自动 |
| 2 | 挑一个还活着、带宽够、在你偏好地区的节点 | ✅ 自动 |
| 3 | 在 mefrp 上建新隧道，记下新的公网端口 | ✅ 自动 |
| 4 | 改本机 `frpc.toml` 的 `serverAddr` / `remotePort` | ✅ 自动 |
| 5 | 重启 frpc 容器 | ✅ 自动 |
| 6 | 去 Cloudflare 改 DNS 记录 | ✅ 自动 |

只有**公网端口变了**这一种情况需要你动手 —— 程序会告诉你「下游哪些反代规则要改」。

## 页面功能

打开 Web UI，顶部六个标签页：

### 总览
落地页。一眼看清当前状态。

- 顶部一行副标题：引擎状态、你的用户组、**节点在线数**（如 `44/44`）、已知节点地址数、当前轮次
- **统计卡**：受管隧道 / 健康 / 异常 / 不探测 / 待确认下游 / frpc 容器状态
- **受管隧道列表**：每条隧道一张卡，显示当前节点、公网入口、端到端探测结果、失败计数、DNS 记录、挂接的 frpc 容器
- 有隧道**没挂接 frpc 容器**时会顶一张琥珀色卡片提醒
- 还在用默认密码的话，顶部挂红色警告

### 隧道
- **上半部分**：受管隧道，每条一张卡片，按钮有
  **立即探测** / **手动切换**（不等判定，马上换节点）/ **挂接 frpc** / **编辑** / **删除**
  （端口变过、还没处理下游的话，还会多一个「下游已处理」）
- 卡片状态有四种：**健康** / **异常** / **在线 · 不探测** / **待探测**。
  「不探测」是 udp 这类做不了 TCP 探测的隧道 —— 只说明**没探**，不是故障，
  所以画成中性提示而不是红色
- **DNS 记录**那一栏要自己到「编辑」里填记录名（例如 `nas.example.com`），
  **填了才会自动同步**；留空 = 这条隧道的 DNS 你自己管
- **下半部分**：mefrp 上**还没纳管**的隧道表格，点「纳管」一键收进来
  （本地地址、端口、当前节点都从 mefrp 实读，不用手填）

### 节点
- 全部节点的表格：节点名 + 地址、区域、带宽、负载、节点上已有隧道数、权限、**可用性**
  - **「可用性」这一列最有用** —— 直接告诉你这个节点能不能被自动选中。不能的话会写明原因
    （带宽不够 / 区域不符 / 在你手工排除的名单里 / 还在冷却期）
  - 命中节点偏好的节点会标 **「偏好 N」**，N 就是它在偏好列表里的顺位
- 顶部一行显示当前的择优规则
- 「排除」/「取消排除」把不想用的节点拉黑；「重新拉取」立即刷新

### frpc 实例
- 每个实例一张卡片：容器状态、重启方式、**当前连的节点**、承载哪几条隧道、配置文件是否已生成、备份份数
- 卡片上的按钮：
  **看配置** / **仅重建**（只写配置文件，不重启）/ **重建并重启** / **只重启容器**
- 「新增实例」登记要控制的 frpc 容器：**配置文件绝对路径** + **容器名** + 重启方式
- 「自动发现绑定」按各容器现有配置里的隧道名，一次性把「哪条隧道归哪个容器」录进来
- 顶部黄色横幅列出还没挂接的隧道

### 事件
按时间倒序的操作日志，故障转移的每一步都在这里，失败也会写明失败在哪一步。

### 设置
凭据、引擎节奏、节点择优、节点偏好、行为开关、账号安全。详见下方「参数设置」。

## 使用逻辑

### 核心模型：一条隧道 : 一个 frpc 容器

一个 frpc 进程只能连**一个**节点。所以**同一个 frpc 容器上的所有隧道必然在同一节点上**。

本程序的模型是**一条隧道配一个 frpc 容器**，每条隧道各自守一个节点、互不牵连 ——
一条隧道要换节点，不会拖着别人一起换。

### 三层健康判定

只看 mefrp 的 `isOnline` 不够（节点列表有 5 分钟缓存，状态会滞后）。所以分三层，任何一层不过就算异常：

| 层 | 判据 | 抓什么 |
|---|---|---|
| 1 · 隧道 | 存在 / 未封禁 / 未禁用 / `isOnline` | 隧道被删了、frpc 没连上 |
| 2 · 节点 | 节点还在 / 未禁用 / 在线 | 节点下线了 |
| 3 · 端到端 | 真的 TCP connect 一次 `节点地址:公网端口` | **唯一不会骗人的判据** |

> ⚠️ **UDP 隧道默认跳过第 3 层。** UDP 在节点上监听的是 UDP 端口，没有 TCP 监听，
> 用 TCP 去探必然失败 —— 会把健康隧道永久误判成故障，然后无限切换。
> 这类隧道在界面上显示为**「在线 · 不探测」**（中性灰），不会画成红色异常。

### 故障转移流程

```
选新节点 → 逐条「删旧隧道 → 建新隧道」（优先沿用原端口）
        → 重建所属 frpc 容器的配置 → 重启那个容器
        → 端到端验证 → 更新 DNS → 推 Gotify
```

其它容器完全不受影响。任一步失败都会明确告诉你失败在哪，不会静默吞掉。

### 防抖

连续失败 `fail_threshold` 次（默认 3）才判故障，避免网络抖动误切。
切换后有冷却期，刚被切走的节点一段时间内不会再选。

### ⚠️ 程序不会自动认领隧道

**首次启动不建任何 frpc 容器，也不会把隧道自动挂到某个容器上。**

挂接必须是**你的一次明确动作**。没挂接的隧道：

- 不会被写进任何 frpc 配置
- **拒绝自动切换**（换节点要改本地配置、重启容器，没有归属就无从下手）
- 总览页、「frpc 实例」页、事件日志三处都会提醒

理由：自动认领会让「没挂接」看起来像「已挂接」，而且一旦你新增一个容器，
这些隧道会突然集体失去归属，行为在那一刻突变。

## 部署安装

### 前置条件

1. **每条要管的隧道，都有一个自己的 frpc 容器**（本程序不创建它，只负责改它的配置并重启它）
2. **mefrp 账号的访问 Token**
3. 要用 DNS 自动同步 → **Cloudflare API Token**（权限 `Zone.DNS:Edit`）
4. 要推送通知 → **Gotify 地址 + App Token**

> ⚠️ 本程序**必须跑在 frpc 所在的同一台机器上** —— 它靠本机的 `docker.sock` 重启容器，跨主机控制不了。

### 方式一：用 Release 里的镜像（推荐）

从 [Releases](../../releases) 下载镜像包 `mefrp-guard-v1.0.1.tar`，和仓库里的
`docker-compose.yml`、`.env.example` 两个文件放在同一个目录，然后：

```bash
# 1. 导入镜像
docker load -i mefrp-guard-v1.0.1.tar
docker images | grep mefrp-guard        # 应看到 mefrp-guard  v1.0.1

# 2. 准备配置
cp .env.example .env
vim .env                                # 至少填 MEFRP_TOKEN、MG_WEB_PASSWORD、FRPC_PATH

# 3. 启动
docker compose up -d
```

> 只要镜像已经导入，compose 就会直接用它，**不会再去本地构建** —— 所以不需要装源码、也不需要 Dockerfile。

> ⚠️ 镜像的 tag 必须和 `docker-compose.yml` 里的 `image:` 一致（默认 `mefrp-guard:v1.0.1`）。
> 不一致的话 compose 会以为本地没有这个镜像，转头去本地构建。

### 方式二：自己构建

```bash
cp .env.example .env
vim .env
docker compose up -d --build            # 等价于 docker build -t mefrp-guard:v1.0.1 . && docker compose up -d
```

想导出成 tar 发给别人：

```bash
docker save mefrp-guard:v1.0.1 -o mefrp-guard-v1.0.1.tar
```

> 镜像 tag 固定成 `v1.0.1` 而不是 `latest`：`latest` 会让「现在跑的是哪一版」变成回答不了的问题，
> 回滚时也没有可指的目标。改了代码就 build 成 `v1.0.2`，`docker compose up -d` 会自动用新镜像重建。

### 升级到新版本

```bash
# 1. 先备份唯一的状态目录
cp -a ./data/prod ./data/prod.bak-$(date +%Y%m%d)

# 2. 导入新镜像、把 docker-compose.yml 里的 image: 改成新 tag，然后
docker compose up -d
```

> **不需要删库重来。** 状态库的结构变更是**启动时自动迁移**的
> （`store.init()` → `_migrate()`）：加字段走 `ALTER TABLE ADD COLUMN`，
> 去约束走「整表重建 + 原样搬数据」（SQLite 不支持 DROP CONSTRAINT）。
> 老库直接拿过来用就行，已有的隧道、事件、设置都会原样保留；迁移是幂等的，
> 重复启动不会重复改动。但**任何自动迁移都值得先备份**，所以第 1 步别省。

### 启动之后

访问 `http://<宿主机IP>:<HOST_PORT>`（默认 `8080`），会先跳到登录页。

**默认账号 `admin` / `admin123`** —— 登录后页面顶部会一直挂红色警告，直到你改掉它。

**唯一需要备份的目录是 `./data/prod`**（状态库、事件日志、frpc 配置备份）。

### 首次配置（照着做一遍）

1. **登录**，然后立刻到「设置 → 账号安全」**改掉默认密码**
2. 「设置」页填 **mefrp Token** → 点「测试」（会显示节点总数、在线数、你的用户组）
3. 填 **Cloudflare Token** → 点「测试」（会列出可管理的 zone）〔不用 DNS 同步可跳过〕
4. 填 **Gotify 地址和 Token** → 点「发条测试消息」〔不用通知可跳过〕
5. 「节点」页点「重新拉取」，把不想用的节点「排除」
6. 「隧道」页把 mefrp 上已有的隧道**纳管**进来，或者「新增隧道」建新的
7. 「frpc 实例」页，**为每条隧道登记它自己的 frpc 容器**（配置路径 + 容器名）
8. 回到「隧道」页，逐条点 **「挂接 frpc」** 挂到对应容器上

> 第 7、8 步不能省 —— 程序不会自动认领隧道。
>
> 如果这些隧道**本来就在某个 frpc 配置文件里跑着**，第 7、8 步可以合并：
> 先把容器登记好，再点「自动发现绑定」一次性把关系录进来。

#### ⚠️ 配置路径填**容器内**路径

「frpc 实例」页要填的是**本程序容器里看到的路径**，不是宿主机路径。

```
宿主机  /srv/frpc/nas/frpc.toml
          ↓  .env 里 FRPC_PATH=/srv/frpc  →  挂载到 /frpc
容器内  /frpc/nas/frpc.toml          ← 填这个
```

填宿主路径的话页面上 `config_exists` 会是 `false`，而「自动发现绑定」遇到读不出来的配置是**静默跳过**的 —— 你只会看到「全都匹配不上」，看不出是路径填错了。

### 不想装 Docker，先试跑

```bash
PY=<python> ./run_local.sh              # 默认监听 127.0.0.1:18080
```

不依赖 Docker，不碰真实 frpc 配置（用 `data/local/` 沙箱目录），鉴权默认开。
代价是没有 `docker.sock` → 「重启 frpc」「看容器日志」不可用，其余功能正常。

### 可选：接入已有 Docker 网络

想让内网反代按固定 IP 指过来（容器重建也不变），在 `.env` 里填：

```bash
CONTAINER_IP=172.20.0.10
EXTERNAL_NETWORK_NAME=docker-net        # docker network ls 里能看到的名字
```

用不到的话，把 `docker-compose.yml` 里 `services` 下的 `networks:` 和文件末尾的顶层 `networks:` **两段一起删掉**即可，走默认 bridge 一样能跑。

## 参数设置

分两层：**`.env`（启动时读，改了要重启）** 和 **Web UI 设置页（存库，即时生效）**。

### `.env` —— 跟宿主机环境有关的

| 变量 | 必填 | 默认 | 说明 |
|---|:---:|---|---|
| `FRPC_PATH` | ✅ | — | 宿主机上**存放所有 frpc 配置的根目录**，挂到容器内 `/frpc` |
| `HOST_PORT` | | `8080` | 宿主机上暴露 Web UI 的端口（容器内固定 8080） |
| `CONTAINER_IP` | | — | 接入外部网络时给本容器的静态 IP |
| `EXTERNAL_NETWORK_NAME` | | — | 要接入的已存在 Docker 网络名 |
| `TZ` | | `Asia/Shanghai` | 时区 |
| `MG_WEB_USER` | | `admin` | 登录用户名（**仅首次启动的种子值**） |
| `MG_WEB_PASSWORD` | | `admin123` | 登录密码（**仅首次启动的种子值**，之后以 UI 里改的为准） |
| `MEFRP_TOKEN` | | — | mefrp Token（仅种子值） |
| `CF_API_TOKEN` | | — | Cloudflare Token（仅种子值） |
| `GOTIFY_URL` / `GOTIFY_TOKEN` | | — | Gotify（仅种子值） |

> `FRPC_PATH` 挂的是**一个公共根目录**，不必给每个 frpc 容器单独挂一行 ——
> 容器内看到的是 `/frpc/<子目录>/frpc.toml`。
>
> `CONTAINER_IP` / `EXTERNAL_NETWORK_NAME` 在 compose 里写成 `${VAR:?…}`，
> 没填会**直接报错并说明缺哪个**，不会静默用错值。

**忘了密码**：删掉库里三行凭据再重启，会用默认密码重新播种。

```bash
sqlite3 ./data/prod/guard.db "DELETE FROM settings WHERE key LIKE 'web_password%';"
docker compose restart
```

### Web UI 设置页 —— 运行期可改

改完点「保存设置」即时生效，不用重启容器。

#### 凭据

| 项 | 说明 |
|---|---|
| mefrp 访问 Token | mefrp.com → 用户设置 → 访问 Token |
| Cloudflare API Token | 权限 `Zone.DNS:Edit`。留空 = 不管 DNS |
| Gotify 地址 / App Token | 留空 = 不推送 |

> 密钥框**留空表示不修改**（避免每次保存都清掉已存的值）。填了就点旁边的测试按钮验一下。

#### 引擎节奏

| 项 | 默认 | 说明 |
|---|---|---|
| 主循环间隔 | `20` 秒 | 多久跑一轮对账 |
| 端到端探测间隔 | `60` 秒 | 单条隧道做 TCP 探测的最小间隔（不是每轮都探） |
| TCP 探测超时 | `4` 秒 | 探测连不上就算失败 |
| **端到端探测模式** | `自动` | 见下 |
| 连续失败几次才切换 | `3` | 防抖，避免网络抖动误切 |
| 切换后冷却 | `300` 秒 | 避免在多个坏节点间反复横跳 |
| 节点冷却 | `1800` 秒 | 刚被切走的节点一段时间内不再选 |

**探测模式**三个选项：

| 选项 | 行为 | 什么时候用 |
|---|---|---|
| **自动**（推荐） | TCP/HTTP/HTTPS 隧道做探测，**UDP 隧道跳过** | 默认，一直用这个 |
| 强制 TCP | 所有隧道都用 TCP 探测 | 只在明确知道后果时用 |
| 关闭 | 只用 mefrp 状态 + 节点状态判定 | 网络环境不适合外连探测时 |

> ⚠️ 选「强制 TCP」会让健康的 UDP 隧道被反复判成故障、**触发无意义的切换**。除非你清楚后果，否则保持「自动」。

#### 节点择优

先**过滤**，再**排序**。

**过滤条件**（不符合的直接出局）：

| 项 | 默认 | 说明 |
|---|---|---|
| 允许区域 | `cn` | 逗号分隔；留空 = 不限 |
| 最低带宽 | `25` Mbps | 带宽不够的不要 |
| 最高负载 | `90` % | 太挤的不要 |

另外还会自动按**用户组权限**（非 VIP 自动排除 VIP 专属节点）和**隧道类型**过滤，以及你手工「排除」的节点和冷却期内的节点。

**排序规则**：`节点偏好顺位 > 手工优先级 > 带宽大 > 负载低`

#### 节点偏好（默认「北京」）

一个**有序列表**，用**包含匹配**去比对节点的**名称 + 描述 + 区域**，命中第几个关键词就排第几档。

- 填「北京」「上海」→ 名字含「北京」的排最前，含「上海」的紧随其后
- **顺序就是优先级**，界面上可以 ↑↓ 调序
- 节点名形如「北京BGP-1」，填「北京」两个字就够，不用写全名
- 一个都没命中的节点排**最后**，但**仍会被选中** —— 偏好是**排序**，不是筛选
- 列表清空 = 所有节点同权，排序退回带宽 / 负载
- 下面有**即时预览**，直接列出每个关键词各自命中哪些节点

> **和「允许区域」的区别**：区域是**筛选**（不符合直接出局），节点偏好是**排序**（不符合只是排后面）。
> 一个是门槛，一个是倾向。

#### 行为开关

| 项 | 默认 | 说明 |
|---|:---:|---|
| 允许自动故障转移 | ✅ | 总开关。关掉 = 只观测不动作（想先跑几天看看效果就关它） |
| 自动纠正漂移的 DNS 记录 | ✅ | 巡检时把 DNS 记录纠到隧道的当前地址。关掉只影响**巡检**；导入 / 探测 / 切换这些你明确点的动作照旧同步 |
| 配置变化后自动重启 frpc | ✅ | 关掉 = 只写配置文件，由你自己重启容器 |
| 未达阈值也推送探测失败 | ⬜ | 开了会比较吵，默认只在**真的切换**时推送 |

#### 账号安全

改用户名或密码**需要先输入当前密码**。改完后其它设备上的登录会全部失效 —— 这是有意的，
否则旧密码泄露期间建立的会话在改密码后依然有效。

## 安全提示

1. **部署到公网前，一定要改掉默认密码**（设置 → 账号安全）
2. 这个服务的鉴权是给**内网**设计的 —— 要暴露到公网，请在 Lucky / Nginx / Cloudflare 上再叠一层访问控制
3. 前面有反代的话，确认它透传了 `X-Forwarded-For`（否则防爆破会把所有人算作同一个 IP）
4. **`docker.sock` 是挂进去的**，等于把宿主机 Docker 的控制权交给了这个容器。三个选择：
   - **接受**（程序只在你自己的内网跑，且只调用「重启指定名字的容器」）
   - **换成 [docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy)**，只放行 `POST /containers/{id}/restart`，然后改 `MG_DOCKER_HOST` 指向代理
   - **不挂**：把 `docker-compose.yml` 里那一行注释掉，「重启 frpc」和「看容器日志」不可用，其余照常（程序会自己降级）

## 已知限制

- **一个 frpc 只能连一个节点**，所以同一个容器上的隧道必须同节点。本项目的模型是**一条隧道一个容器**，各自守一个节点。
- **隧道必须手动挂接**，程序不做任何自动认领。代价是初次配置多两步（登记容器 + 挂接隧道）。
- **⚠️ 非管理员账号拿不到「还没有隧道」的节点的公网地址**（mefrp 侧的权限限制）。
  对这种全新节点做不了端到端探测 → 切过去之后验证会降级为「无法验证」。
  （DNS 同步不受影响：解析的是地址，跟能不能探测没关系。）
  想彻底解决就得给 mefrp 账号加管理员权限。
- **UDP 隧道做不了端到端探测**（TCP 探测对 UDP 端口必然失败），所以这类隧道只显示
  「在线 · 不探测」。它的 DNS 照常同步，只是「通不通」得靠业务侧自己看。
- **DNS 只在「隧道上填了记录名」时才管**。记录名在「编辑隧道」里填，格式是 Cloudflare
  上的完整记录名（例如 `nas.example.com`）。填了之后程序会在**导入时、每次探测、以及
  每轮巡检**时把这条记录纠到隧道的当前地址上；留空 = 这条隧道的 DNS 你自己管。
  记录所在的 zone 必须在 API Token 的可见范围内（权限 `Zone.DNS:Edit`）。
- **DNS 记录名必须全局唯一**（隧道名不是 —— 那个只在同一台 frps 内唯一，重名合法）。
  两条隧道填同一个记录名会被拒绝：它们会每轮互相覆盖同一条记录，解析结果反复翻面。
  想换名字直接改就行，旧名字当场释放。
- 端到端探测只能证明 **TCP 层可达**，不能证明后端服务健康。UDP 隧道更没有可靠的端到端探测手段。
- 隧道被 mefrp 判为 `isBanned` 时不会自动处理 —— 这类问题通常需要人工申诉，换节点也会继续被封。
- 事件日志默认保留最近 5000 条。

## 更新日志

### 1.0.1

- **修：外部节点的隧道「没自动解析 DNS」。** 前提是隧道上填了 DNS 记录名（见「已知限制」），
  但只要填了就不该被跳过 —— 而原来三条独立的路各自把它漏掉了：① **udp 隧道**在 `auto`
  模式下不做 TCP 探测，引擎在这个分支**直接跳过**，于是 udp 的外部隧道**永远**同步不了
  DNS —— 而 udp 恰恰是外部节点上最常见的一类；② 「立即探测」按钮里同款分支也一样漏；
  ③ 导入时压根不同步，全靠引擎下一轮巡检（最长 20 秒），粘完配置什么都不发生。
  现在三条路都补齐，探测和导入的结果里都会**当场**回话（成功 / 找不到 zone / token 没权限）。
- **修：`last_error` 不再把「不适用探测」画成红色故障。** udp 隧道探不了 ≠ 隧道坏了。
  「探不了」的原因现在走中性的 ⓘ 提示，老版本留下的红字也会在下一轮自动清掉。
- **修：mefrp 挂了不再连累外部节点。** 引擎原来在「没配 mefrp Token」和「拉取 mefrp
  失败」时整轮直接返回，于是自建节点上的隧道跟着一起瞎掉（探测不更新、DNS 不解析）。
  现在这种时候**只**对账外部节点的隧道 —— 反过来放行 mefrp 隧道是危险的：proxy 列表
  是陈旧的，会判出假故障、一路累积到触发一次不该发生的切换。
- **修：隧道名的唯一性被当成了「全局」。** 隧道名其实只在**同一台 frps 内**唯一
  （mefrp 的一台 = 整个账号；外部节点的一台 = 那个节点），**不同运营商之间重名完全合法**。
  原来的全局查重有三个后果：导入一份含同名隧道的外部配置时那条隧道会被当成「已纳管」
  **直接吞掉**（还留下一个空节点）；展示名重名会被强行改成 `xxx-数字`；手动改成已存在的
  名字会直接 **500**。现在查重一律按作用域进行。
- **修：「这个地址已经导入过了」原来是一条死路。** 提示让你去编辑那个节点，但**零隧道的
  残留节点在页面上没有任何入口能到达它**（节点不进节点页、隧道卡片按隧道渲染，没隧道就没卡片）
  —— 改不了也删不掉，重新导入永久被堵。现在冲突响应会带上节点 id 与两个计数，页面上给出
  「打开这个节点的配置」和「清掉它并重新导入」（只对空节点开放，有隧道挂着的一律拒绝）。
- **修：** CF 请求失败的日志里现在会带上异常类型 —— 超时类异常的说明常常是空串，
  以前日志里只剩一句「请求 Cloudflare 失败：」，完全看不出是超时、连不上还是 TLS 出错。
- **修：没配 Cloudflare Token 时不再刷事件日志。** 以前每条填了 DNS 记录名的隧道
  每轮巡检（默认 20 秒）都会记一条「更新 DNS 失败：尚未配置 Cloudflare API Token」，
  很快把日志刷满，真正的问题反而被淹掉。现在只在**你明确点动作**（导入 / 探测 / 切换）
  时才回话。
- **新：隧道标签。** 可筛选、可批量打标，用来区分不同来源的同名隧道（`mefrp` 自动打上，
  外部节点的隧道留给你自己填）。
- **新：外部节点是隧道的附属信息。** 从 frpc 配置导入、跟着隧道走；「换节点」是**实例级**
  动作，入口统一在 frpc 页的「改连外部节点」和隧道卡片上。实例改连后会自动清理没人引用的旧节点。
- **改：** 节点页明确标注为 mefrp 纳管的节点；外部节点（没有 API）不进节点页。
- **改：** 「编辑隧道」里的 `mefrp 隧道名（proxyName）` → `隧道名（proxyName）`。
- **修：DNS 同步不再「一抖就红」。** 三个问题叠在一起，会让一次网络抖动看起来像 DNS 功能
  坏了：① `_sync_dns` 的**写路径上要打 4 个请求**（自己查一次 + `upsert` 内部又查两次 +
  写入一次），而客户端**每个请求都新建一个连接池** —— 也就是 4 次全新的 TLS 握手，彼此
  不复用；巡检每 20 秒就来一轮，握手次数把「握手中途超时」的概率直接放大了（从国内连
  Cloudflare，一次握手几百毫秒到一秒多很正常）。② **零重试**，超时一次整条同步就失败。
  ③ 失败**一律记 error**，于是事件日志里出现一条条红色的「更新 DNS 失败」，而下一轮立刻
  又好了。现在：连接池复用（一次握手撑很多轮）、写路径 4 个请求降到 2 个、传输层失败退避
  重试 2 次。
- **改：瞬时 DNS 失败先记 `warn`，连续 3 次才升 `error`。** 「网络抖了一下」和「配置真错
  了」（token 没权限、找不到 zone）现在能分得清：前者多半等一下就好，后者得你去改配置。
  你明确点的动作（导入 / 立即探测 / 切换）不受这个阈值影响，照旧如实报。
- **新：DNS 记录名查重。** 两条隧道填同一个记录名会被**硬拒绝**（409，并带上占用者的 id
  和名字）—— 因为它们会每 20 秒对着同一条记录互相覆盖，解析结果反复翻面，而日志里只有
  一行行「DNS 已更新」，完全看不出在打架。导入外部节点时撞名则**只放弃这一个字段**
  （隧道照建，结果里单独报出来）。⚠️ 注意：**隧道名**的重名是合法的（只在同一台 frps 内
  唯一），被拒的只有 DNS 记录名。
